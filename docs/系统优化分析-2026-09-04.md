# yixian-notes-v3 系统优化分析（2026-09-04）

## 0. 说明

本报告基于当前仓库源码、现有构建产物、`npm run build` / `npm run size` 结果，以及本地 `vite preview` 浏览器实测数据整理。

需要特别说明两点：

1. 当前仓库已经做过一轮前端分包与懒加载优化，不是完全未优化状态。
2. 项目尚未建立统一的运行时性能遥测与 Tauri IPC/SQLite 基准测试，因此“前端首屏/资源体积”已有实测，“后端接口 P95 / SQL 响应耗时”目前只能给出代码级瓶颈判断与后续补测方案，不能伪造生产值。

## 1. 项目基线档案

### 1.1 技术栈与运行形态

- 前端：`React 19 + TypeScript + Vite 5 + Tailwind CSS 4 + React Router 7 + Zustand`
- 桌面端：`Tauri 2`
- 后端：`Rust + rusqlite + r2d2`
- 数据层：`SQLite（bundled）`
- 重型功能依赖：
  - 图表：`echarts`
  - Markdown/公式/图表：`react-markdown + rehype/remark + katex + mermaid`
  - OCR：`tesseract.js`（前端）+ Windows OCR（Rust）
  - 导入导出：`jszip`、`qrcode`
- 发行产物：`NSIS`、`MSI`、便携压缩包

### 1.2 当前核心业务模块

- 工作区与布局：`src/components/layout/LayoutManager.tsx`
- 笔记主链路：`NotesWorkspace / Tag / Notebook / Search`
- 执行域：`Todos / Reminders / Calendar / FourQuadrant / Pomodoro`
- 知识扩展：`Flashcards / Markdown / Mermaid / ECharts`
- 工具域：`Clipboard / OCR / ImportExport / Vault / WebsiteNavi`
- 桌面增强：浮动便签、悬浮图片/文本、托盘、快捷键、多窗口

### 1.3 当前构建与部署链路

- Web 构建：`npm run build` -> `tsc + vite build`
- 体积报告：`npm run size` -> `scripts/size-report.mjs`
- 桌面构建：`npm run tauri:build`
- 发版脚本：`scripts/release.mjs`
- Tauri 构建前置：
  - `beforeBuildCommand`: `npm run build`
  - `frontendDist`: `../dist`

### 1.4 代码与架构现状

- 已有优化：
  - Vite `manualChunks`
  - 路由级 `React.lazy`
  - `echarts / mermaid / tesseract` 已做懒加载
  - Rust `release` 已开启 `opt-level = "z" + lto + strip + panic=abort`
- 主要架构现状：
  - 仍存在 `localStorage + MOCK 数据 + SQLite` 三套数据来源并存
  - `LayoutManager` 承担了过多聚合、状态拼装和 context 分发职责

## 2. 核心问题总览

### 2.1 性能侧

1. 首屏被远程字体 CSS 阻塞，且其体积高于主入口 JS。
2. 主入口仍静态挂载过多全局能力，导致关键 JS 达到 `879 KB`。
3. `Dashboard`、`NotesWorkspace` 等页面仍有大量列表过滤、排序、统计计算在渲染期重复执行。
4. 虚拟列表能力已有实现，但未覆盖所有高频长列表页面。
5. 后端搜索仍以 `LIKE` 为主，尚未进入 FTS/索引驱动模式。
6. 当前没有统一的 IPC/SQL 性能基准、慢查询日志和启动性能历史看板。

### 2.2 体积侧

1. Mermaid 生态相关 chunk 是当前最大前端体积来源。
2. `framer-motion` 为大量页面常驻依赖，抬高启动关键 JS。
3. `ImportExport`、`OCR`、Markdown 增强能力虽然部分懒加载，但仍有继续收口空间。
4. 仍存在疑似未充分使用或可替换依赖。
5. 桌面端 Rust 依赖已做 release 优化，但功能 feature 仍偏宽。

### 2.3 扩展性侧

1. `LayoutManager + useNoteOperations + Repository` 仍偏“总线化”，模块边界不够清晰。
2. `localStorage / SQLite / MOCK` 并存，真实数据源不唯一。
3. 多个页面直接引用 `MOCK_*`，说明领域抽象尚未彻底完成。
4. 业务功能以页面内聚合实现为主，缺少可插拔的模块注册与扩展点。
5. 当前实现强依赖 Tauri API，Web/多端适配边界未抽象。

## 3. 可落地优化清单

以下按优先级排序，默认分为 `P0（立即执行）/ P1（近期执行）/ P2（中期治理）`。

### 3.1 P0：高收益、短路径优化

#### 1. 首屏字体本地化与子集化（P0｜高收益｜低复杂度）

- 证据：`src/index.css` 通过远程 `@import` 加载 Google Fonts；首屏字体请求约 `242 KB`。
- 预期收益：
  - FCP 从 `~512 ms` 降到 `<= 350 ms`
  - 首屏传输量减少 `180~260 KB`
  - 消除外网依赖和字体服务不稳定风险
- 实施步骤：
  1. 将 `Noto Sans SC / Noto Serif SC` 改为本地静态资源或系统字体栈。
  2. 如必须保留字体，使用子集字体，仅保留常用字重。
  3. 将字体声明从 `@import` 改为本地 `@font-face` 或系统回退栈。
- 技术方案：优先改为 `system-ui + Segoe UI + PingFang SC + Microsoft YaHei`；如需品牌字体再做本地子集包。
- 验证标准：
  - 首屏不再出现外域字体请求
  - `FCP <= 350 ms`
  - 首屏资源数保持不增

#### 2. 继续压缩启动关键 JS（P0｜高收益｜中复杂度）

- 证据：启动关键 JS 仍为 `879 KB`，其中 `main + react-vendor + motion-vendor + icons-vendor + date-vendor` 常驻。
- 预期收益：
  - 启动关键 JS 降至 `<= 600 KB`
  - 主包 `main` 降至 `<= 280 KB`
- 实施步骤：
  1. 将全局悬浮窗、快捷入口、托盘桥接等能力按窗口/路由再拆分。
  2. 避免在入口静态引入不属于首屏的 Tauri API。
  3. 将 `FloatingStickies`、`LocalSearchOverlay`、`WorkspaceQuickSwitcher` 的初始化再后置。
- 技术方案：基于当前 `React.lazy` 继续拆到“首屏只保留 Dashboard 必要路径”。
- 验证标准：
  - `npm run size` 中 `startupJSKB <= 600`
  - 浏览器首屏请求的 JS 数量不明显增加

#### 3. Dashboard 延迟图表挂载与计算下沉（P0｜高收益｜中复杂度）

- 证据：`DashboardPage.tsx` 文件体积大，内部存在大量 `filter/sort/map` 统计计算和 ECharts 使用。
- 预期收益：
  - 降低首页渲染主线程占用
  - 降低进入 Dashboard 时的卡顿峰值
- 实施步骤：
  1. 把统计计算抽到独立 selector / service。
  2. 图表区域改成进入页面后 `idle` 或可见时再挂载。
  3. 对高成本统计建立工作区级缓存。
- 技术方案：`requestIdleCallback` / IntersectionObserver + memoized selectors。
- 验证标准：
  - 首页渲染不再伴随明显掉帧
  - React Profiler 中 Dashboard 首次 commit 时间明显下降

#### 4. NotesWorkspace 继续拆页与拆逻辑（P0｜高收益｜中复杂度）

- 证据：`NotesWorkspacePage` chunk `~288 KB`，`NoteListPane.tsx`、`EditorPane.tsx` 都偏大。
- 预期收益：
  - 主工作区切换更顺滑
  - 后续功能迭代时局部修改不再放大全页回归风险
- 实施步骤：
  1. 将笔记列表、编辑器工具条、版本记录、标签面板、批量操作拆成独立子模块。
  2. 将筛选/排序逻辑下沉到 selector 层。
  3. 将导出、批量操作、上下文菜单能力按需加载。
- 技术方案：`feature folder + selector + lazy panel`。
- 验证标准：
  - `NotesWorkspacePage` chunk 降至 `<= 180 KB`
  - NoteList 交互不出现明显重渲染尖峰

#### 5. 长列表虚拟化扩面（P0｜中高收益｜低复杂度）

- 证据：已有 `useVirtualList` 与 `VirtualList`，但 `WebsiteNavi`、`Clipboard`、`Reminders`、`Notifications` 等仍有大量直接 `map` 渲染。
- 预期收益：
  - 千级数据时滚动更稳
  - 降低 DOM 数量和内存占用
- 实施步骤：
  1. 优先覆盖 `Clipboard / Notifications / Reminders / WebsiteNavi / FlashThoughts`。
  2. 为高度相对稳定的卡片列表优先使用固定高度虚拟化。
  3. 对分组列表增加分段渲染。
- 技术方案：复用现有 `useVirtualList`，无需引入新库。
- 验证标准：
  - 1000 条数据时滚动保持流畅
  - DOM 节点数量明显下降

#### 6. Mermaid 能力按需收口（P0｜高收益｜中复杂度）

- 证据：Mermaid 相关 chunk 累计是前端最大体积热点，含 `mermaid.core / cynefin / cytoscape / diagram-*`。
- 预期收益：
  - `dist` 体积降低 `1.5~2.5 MB`
  - Markdown 首次打开图表场景更可控
- 实施步骤：
  1. 限制默认支持的 Mermaid diagram 类型。
  2. 将高成本图类型设为二级懒加载或实验能力。
  3. 评估切换到更轻量的图表渲染策略。
- 技术方案：保留常用 `flowchart / sequence / gantt`，重型图类型通过 feature flag 开启。
- 验证标准：
  - `dist` 总量降至 `< 5 MB`
  - Mermaid 常用能力不回退

#### 7. SQLite 搜索升级为 FTS5 + 结果投影（P0｜高收益｜中复杂度）

- 证据：`search_notes`、`cross_search` 当前主要使用 `LIKE`，对中大数据量不友好。
- 预期收益：
  - 搜索响应从“数据量线性变差”转为稳定
  - 为全局搜索、标签联想、笔记联想提供基础设施
- 实施步骤：
  1. 为 `notes / todos / captured_items` 建立 FTS5 虚表。
  2. 查询只返回列表页所需字段，避免大文本整列回传。
  3. 增加关键词高亮片段生成。
- 技术方案：`contentless/content=xxx FTS5 + triggers` 或保存时同步写入索引表。
- 验证标准：
  - 5000 笔记数据集下搜索 `P95 <= 100 ms`
  - 返回字段体积明显下降

#### 8. 建立真实性能基准与慢路径采样（P0｜高收益｜低复杂度）

- 证据：当前只有 `src/lib/perf.ts` 和 `scripts/size-report.mjs`，缺少统一看板。
- 预期收益：
  - 后续每次优化都能量化验证
  - 避免“感觉变快/变小”的主观判断
- 实施步骤：
  1. 扩展 `perf.ts`，记录启动、路由切换、重型页面打开耗时。
  2. 为 Rust 命令增加分段耗时日志。
  3. 生成 `performance/baseline-*.json` 历史记录。
- 技术方案：前端 Performance API + Rust tracing + 手动 benchmark 命令。
- 验证标准：
  - 每次构建后自动输出 baseline
  - 能比较优化前后百分比变化

### 3.2 P1：近期执行的瘦身与结构优化

#### 9. 清理或替换低价值依赖（P1｜中收益｜低复杂度）

- 当前候选：
  - `@tauri-apps/plugin-updater`：仓库内未见实际接线
  - `react-error-boundary`：项目已有自定义 `ErrorBoundary`
  - `@types/jest`：当前测试栈为 `vitest`
  - `next-themes`：当前只在 `sonner` 主题层使用，可改为接现有 settings 主题
- 预期收益：依赖树更干净、安装体积更小、构建分析更清晰。
- 实施步骤：
  1. 逐个确认引用与替代方案。
  2. 删除未使用依赖并回归构建/测试。
  3. 为每个保留的大依赖补“为什么保留”的说明。
- 验证标准：
  - `npm ls --depth=0` 更简洁
  - `package-lock.json` 体积下降

#### 10. Import/Export/OCR/QR 能力再延迟加载（P1｜中收益｜低复杂度）

- 证据：`ImportExportPage` 入口已较大，`qrcode`、`jszip`、OCR 仍可进一步按动作延迟。
- 预期收益：
  - 降低非导入导出用户的负担
  - 降低首开工具页抖动
- 实施步骤：
  1. `qrcode` 改为点击“生成二维码”时再 import。
  2. `jszip` 改为处理 zip 文件时再 import。
  3. OCR 保持按钮级加载，不提前初始化 Worker。
- 验证标准：
  - `ImportExportPage` chunk 继续下降
  - 默认工作流不再加载这些库

#### 11. 动画策略分层（P1｜中收益｜中复杂度）

- 证据：`framer-motion` 在大量页面广泛使用，导致 `motion-vendor` 常驻 `123.7 KB`。
- 预期收益：
  - 启动 JS 继续下降
  - 低配机器 UI 更稳
- 实施步骤：
  1. 将纯淡入/位移动画替换为 CSS transition。
  2. 保留真正需要布局动画的少数交互。
  3. 对列表卡片默认降级动画。
- 验证标准：
  - `motion-vendor` 明显缩小或只在部分路由加载
  - UI 交互不出现视觉倒退

#### 12. 后端查询字段瘦身与聚合接口（P1｜中收益｜中复杂度）

- 证据：多个查询直接返回完整内容列，如 `notes.content`；列表态其实只需要摘要。
- 预期收益：
  - IPC 负载下降
  - 列表加载更快
- 实施步骤：
  1. 区分 list/detail DTO。
  2. 为 Dashboard / Search / Sidebar 补聚合接口，避免前端二次遍历大集合。
  3. 对常用统计提供后端聚合结果。
- 验证标准：
  - 列表接口返回 JSON 体积下降
  - Dashboard 不再依赖全量对象自行汇总

#### 13. Rust feature 再裁剪（P1｜中收益｜中复杂度）

- 证据：发行包已经不大，但 `windows`、`reqwest`、`tokio full`、`image` 等 feature 仍有收窄空间。
- 预期收益：
  - 构建时间下降
  - 安装包体积再缩 `5%~15%`
- 实施步骤：
  1. 将 `tokio = { features = ["full"] }` 收窄到实际所需。
  2. 审核 `reqwest` 是否只需 `json + rustls-tls`。
  3. 收窄 `windows` crate feature。
- 验证标准：
  - `cargo bloat` / 发行包体积下降
  - 构建功能不回退

#### 14. 构建卫生与产物治理（P1｜中收益｜低复杂度）

- 证据：仓库中保留了大量 `src-tauri/target/release` 中间产物，容易影响分析与协作。
- 预期收益：
  - 仓库更干净
  - 产物分析更准确
- 实施步骤：
  1. 明确 `dist / target / bundle / portable` 的归档策略。
  2. 为发版脚本增加产物清理与产物摘要输出。
  3. 补充 `.gitignore` / 文档说明。
- 验证标准：
  - 产物目录职责清晰
  - 发版物与中间物可区分

### 3.3 P2：扩展能力与中期架构治理

#### 15. 统一真实数据源，移除 MOCK 并退役 localStorage 主链路（P2｜高收益｜高复杂度）

- 证据：`useNoteOperations`、`notesRepository`、多个页面仍直接依赖 `MOCK_*` 或 `localStorage`。
- 预期收益：
  - 数据一致性问题显著减少
  - 同步、备份、搜索、扩展插件都有统一基础
- 实施步骤：
  1. 以 SQLite 作为唯一真源。
  2. localStorage 只保留 UI 偏好与短期缓存。
  3. 删除页面中的 `MOCK_*` 直接引用。
- 验证标准：
  - 搜索 `MOCK_` 仅剩测试文件
  - 所有核心业务对象都从 repository/service 读取

#### 16. 完成 Service / Repository / Hook 分层迁移（P2｜高收益｜高复杂度）

- 证据：当前 Hook 中仍夹杂领域规则、状态组织、持久化和 UI 衍生逻辑。
- 预期收益：
  - 扩展新对象模型更容易
  - 回归测试边界更清晰
- 实施步骤：
  1. Repository 只负责数据访问。
  2. Service 负责业务规则、聚合、缓存、派生。
  3. Hook 只做页面组合与事件桥接。
- 验证标准：
  - 页面不再直接处理存储细节
  - Hook 文件体积明显下降

#### 17. 拆解 LayoutManager 的“总线化”职责（P2｜高收益｜中复杂度）

- 证据：`LayoutManager.tsx` 聚合了工作区、提醒、主题、引导、浮窗、快捷键、context 构建等多类职责。
- 预期收益：
  - 扩展新模块时不再频繁动入口大文件
  - 降低上下文级联重渲染
- 实施步骤：
  1. 拆为 `WorkspaceShell / DesktopBridge / FeatureProviders / AppContextFactory`。
  2. 将大型 context 拆成多 context 或 selector 型 store。
  3. 避免单次 render 传递超大对象。
- 验证标准：
  - LayoutManager 文件显著瘦身
  - 不相关功能切换不触发全局重渲染

#### 18. 建立模块注册表与 feature flag（P2｜中高收益｜中复杂度）

- 目标：让 `OCR / Vault / WebsiteNavi / Flashcards / AI` 等能力可配置启停。
- 预期收益：
  - 支撑精简版 / 完整版 / 工作区差异化能力组合
  - 为多端裁剪准备条件
- 实施步骤：
  1. 建立统一模块声明表（路由、导航、依赖、权限、开关）。
  2. 页面入口按模块注册自动生成。
  3. 构建期与运行期都支持开关。
- 验证标准：
  - 关闭模块后不再进入导航、路由与构建主链

#### 19. 抽象 Tauri 边界，预留 Web / 多端适配入口（P2｜中收益｜高复杂度）

- 证据：当前多处直接 `import("@tauri-apps/api/...")`。
- 预期收益：
  - 后续扩到纯 Web、移动端壳或多前端实现时更顺
  - 非 Tauri 环境调试成本下降
- 实施步骤：
  1. 建立 `platform adapter` 层。
  2. 将窗口、文件、通知、快捷键、托盘统一走 adapter。
  3. 为非 Tauri 环境提供 mock/降级实现。
- 验证标准：
  - UI 层不再直接依赖 Tauri 包

#### 20. 建立自动化性能守门（P2｜中收益｜中复杂度）

- 目标：把优化结果固化到 CI 或本地检查。
- 实施步骤：
  1. 固定输出 `size-report.json`
  2. 补 `build budget` 与关键 chunk budget
  3. 增加启动时序、搜索耗时、列表渲染 benchmark
- 验证标准：
  - 超预算直接报警
  - 优化不会被后续迭代反向冲掉

## 7. 结论

这个项目当前的主要矛盾已经很清楚：

1. **前端不是“功能不够”，而是“重型能力已经堆起来了，但首屏与主链路还没有彻底分层”**。
2. **后端不是“没有优化”，而是“已有连接池和基础索引，但搜索与聚合还停留在过渡态”**。
3. **最关键的扩展瓶颈不是单个页面慢，而是数据真源、模块边界、平台边界还没有完全收口**。

如果按本报告的优先级推进，第一轮就能同时拿到三类明确收益：

- 体感启动更快
- 前端包体更小
- 后续继续扩功能时不再越来越难维护

### 8.2 本次新修复（非文档原项）

**`cross_search` LIKE 布尔优先级 bug**（`src-tauri/src/storage/objects.rs`）：
- 原：`title LIKE ?1 OR content LIKE ?1 AND is_favorite = 0`
- 修复：`(title LIKE ?1 OR content LIKE ?1) AND is_favorite = 0`
- 原因：SQL 运算符优先级导致 `AND` 仅作用后半段，「收藏但标题命中」的笔记被错误过滤。已 `cargo check` 通过。
